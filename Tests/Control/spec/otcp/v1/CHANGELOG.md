# Changelog

All notable changes to the OTCP specification are recorded here. Versions follow `MAJOR.MINOR.PATCH` (README.md, "Versions"); each released version is tagged `spec-v<version>`.

## [1.0.0-rc.3] - unreleased

Third release candidate of protocol major 1. It records what implementing the methods against OpenTune showed: where OpenTune behaves differently from what rc.2 assumed, which failures had no reason code, and where the specification left a choice open. The wire version stays `1.0`, and no member, code, capability or vector is removed or renamed. Three behaviours are tightened (listed under "Changed"): `timeGrid.minHandleSpacingSec` of `content.getDetails` is always present, deletions list the contents they remove, and an export without audio fails. Where the reference implementation does not send a new reason or warning yet, the text says that an implementation of this release candidate may leave it out.

### Added

- Registries: reason codes `content_key_unset` and `nothing_to_export` (`INVALID_ARGUMENT`), `export_dry_stretched`, `export_stretch_dropped` and `timing_analysis_timeout` (`NOT_READY`) and `timing_analysis_failed` (`ANALYSIS_FAILED`); warning code `IMPORT_COMMIT_REPEATED`. No error kind or capability is added.
- `content.autoTune` (mode `reference`) and `content.analyzeReference`: the `referenceAnalysis` job repeats the checks of the call when it runs and fails with their errors, so `x-otcp.jobErrors` lists `INVALID_ARGUMENT`, `NOT_FOUND` and `NOT_READY`, and for `content.autoTune`, whose job writes, also `BUSY`.
- `content.editTimeGrid`: the timeGridSeed job fails with `ANALYSIS_FAILED(timing_analysis_failed)` when OpenTune's timing analysis fails or finds no onset, and with `NOT_READY(timing_analysis_timeout)` when it does not finish within the job's wait limit; `x-otcp.jobErrors` adds `ANALYSIS_FAILED`.
- PROTOCOL.md section 19 rule 6: a content whose time grid is not the identity is exported from time-stretched audio; the job waits for it, and ends early with `NOT_READY(export_dry_stretched)` or `NOT_READY(export_stretch_dropped)`. Rule 11 says which of the new reasons an implementation of this release candidate may still leave out.
- `content.getDetails`: `timeGrid.nullReasons`, for a `minHandleSpacingSec` the server cannot determine.
- `import.start`: the warning `IMPORT_COMMIT_REPEATED` when OpenTune refused a clip id that the project already used and the job committed the clip again.
- Vectors `content/analyze-reference-job-failures` (the errors of the referenceAnalysis job) and `export/start-nothing-to-export`; `content/edit-time-grid-job-failures` shows the two new seed failures.

### Changed

- `content.getDetails`: `timeGrid.minHandleSpacingSec` is required; it is null, with `timeGrid.nullReasons.minHandleSpacingSec` `unavailable`, when the server cannot determine it. The vector `content/get-details-ok` expects it.
- PROTOCOL.md section 14.4 rule 6: a content that leaves the project because a write removed the last clip that showed it is listed in `removed` (entity `content`), after the clips. The vectors `arrangement/edit-delete`, `track/delete-ok` and `edit/undo-content-removed-with-track` list it.
- PROTOCOL.md section 19 rule 1: an export that would hold no audio (a track without clips, a master mix in which no clip is heard) fails at once with `INVALID_ARGUMENT(nothing_to_export)` instead of writing a file without audio.

### Clarified

- PROTOCOL.md section 8.2: a server rounds each kind of value alike in every result, so that a write reports what a later read returns; OpenTune's implementation rounds `Midi` and `Cents` values to 4 decimal places. `content.getNotes`: `detectedMidi` keeps its fraction.
- PROTOCOL.md section 9: notes that start at the same time keep the order in which OpenTune stores them, and reads and write results count in this one order. Section 14.3: `after` in `changes` is read back from the committed state, never the requested value.
- PROTOCOL.md section 10 rules 2 and 6, `content.getNotes` and `content.getPitchCurve`: the pitch shift moves `targetMidi`, `detectedMidi` and `correctedMidi` without changing `revision`, and the cursors of both reads are bound to the pitch shift.
- PROTOCOL.md section 12.1, section 12.5 and `methods/README.md`: a job's result is defined by the method that started it, not by its kind; `content.analyzeReference` returns only jobs that it started; a reader that does not know the starting method accepts a result that is valid for one of the methods that start that kind.
- PROTOCOL.md section 15.3 rule 8: a server MAY withdraw the `undoId` it assigned to an entry recorded in the UI when it can no longer confirm that entry, as after OpenTune's history (500 entries) dropped its oldest entry; a call that names a withdrawn `undoId` fails with `UNDO_CONFLICT(top_mismatch)`.
- PROTOCOL.md section 15.3 rule 9: the rule that a change without an undo entry clears the redo history differs from the OpenTune UI, which keeps its redo history when the key is changed there; the rule stays for this release candidate.
- PROTOCOL.md section 15.4 rule 7 (new): OpenTune shortens a note that overlaps the next one when it commits notes, which write results report and predictions do not show; it does not commit an edit of a note of zero duration, which is predicted but fails with `INTERNAL` when committed.
- PROTOCOL.md section 19, "Hybrid mode" (informative), and the descriptions of `hybridMode` in `prefs.get`, `session.info` and `export.start`: with hybrid mode on, OpenTune renders small corrections with a pitch shift instead of the vocoder, so reported corrected pitch can differ from what is heard; the threshold is not part of the protocol.
- PROTOCOL.md section 20.3 rule 4: a loaded media file on a volume that is not available makes every export fail with `IO_ERROR(read_failed)`.
- PROTOCOL.md section 21 rule 1 and `content.getDetails`: an instance that does not report `reference.v1` reports `uiButtonRuns` `regenerate` even where OpenTune's AUTO button would run reference alignment because of a binding left on the clip; clients that describe the button check `reference.referencePlacementId` and the experimental features.
- PROTOCOL.md section 21 rule 2 and `import.start`: two intended differences from the import of the OpenTune UI, in the `openDyne` scheme (notes only for the focused clip) and in layout `separateTracks` (files are appended after the last clip of their track, not placed at timeline 0).
- `content.editNotes` and `content.autoTune`: `setTargetPitch` and `snapToScale` set the base pitch with `offsetCents` 0, while mode `snapNotes`, like OpenTune's own snap, keeps the base pitch, sets `offsetCents` and snaps from the base pitch alone; `clipKey` on a content without a key gives `INVALID_ARGUMENT(content_key_unset)`.
- `content.editTimeGrid`: seeding a grid that already has handles still hands the work to a job, whose result is a no-op; the methods of `timing.v1` do not depend on OpenTune's experimental features, which its UI requires for the time tool.
- `export.start`: the new reasons and the unavailable volume in the description.
- `content.autoTune`: the order in which the reference job repeats its checks is not part of the contract.
- vectors/README.md: `extraCapabilities`, like `capability`, is decided before `given`; a runner that cannot create a `noAccess` directory, which on Windows needs an access control list, skips the vector with that reason. `track/duplicate-target-occupied`: how OpenTune reaches a hidden track that holds clips.

## [1.0.0-rc.2] - unreleased

Second release candidate of protocol major 1. It defines the schemas of the methods that 1.0.0-rc.1 listed as planned, so that every method of version 1 now has a normative schema, and it settles questions that 1.0.0-rc.1 left open. It adds to 1.0.0-rc.1; the behaviour changes listed under Clarified tighten two rc.1 behaviours (`import.start` with `newTrack` when every track holds clips, and section 15.3 rule 9): no member, code, capability or vector is removed or renamed, and the expectations of the existing vectors are unchanged. The one member that servers of 1.0.0-rc.1 must add is `contents` of the `export.start` job result; the entries under "Clarified" say where else their behaviour has to follow this version.

### Added

- Method schemas: `ui.getState` and `ui.dismiss` (layer L3); `transport.control`, `transport.setTempo`, `transport.setLoop`, `arrangement.edit`, `arrangement.copy`, `track.set`, `track.add`, `track.duplicate`, `track.delete`, `ui.setSelection` and `content.analyzeReference` (layer L6); `project.save`, `project.saveAs`, `project.open`, `project.clearRecent`, `prefs.set`, `audio.get` and `audio.set` (layer L8). `methods/index.json` and the method table of PROTOCOL.md section 22 list them as defined.
- The full behaviour of `content.autoTune` in mode `reference`: its job computes missing alignment data as `content.analyzeReference` does and then aligns the content in one undo step; a reference binding left on a clip makes OpenTune's AUTO button run reference alignment, which `content.getDetails` reports and which `content.autoTune` never infers.
- The `export.start` job result lists in `contents` the revision of every content in the file, as the job recorded it when all contents were ready, so that a client can tell whether edits made after `export.start` are in the file (PROTOCOL.md section 19 rule 10).
- PROTOCOL.md: `ui.dismiss` is not refused because a dialog is open (section 13.2); the entity names `selection` and `audioDevice`, and references `{singleton: <entity>}` for entities of which an instance has one (section 14.3, `common.schema.json#/$defs/entityRef`); view state (play state and position, loop flag, selection, workspace, visible track count, dialogs, shown scale) is exempt from the revert rules and carries no `IRREVERSIBLE` for its own change (section 15.2 rule 6); `ui.dismiss` refuses to close a dialog that commits on close with `INVALID_ARGUMENT(dialog_commits_on_close)` (section 15.4 rule 4); `content.analyzeReference` returns the job that runs for the same placement (section 12.5); `project.open` takes the end user's consent as `discardUnsaved`, and `arrangement.edit` with op `delete` and `ui.dismiss` closing a dialog that commits the value it shows take it as `confirm`, and a prediction (`dryRun`) needs no consent (section 20.2 rule 3); switching to `openDyne` reports generated notes with `SCHEME_GENERATED_NOTES` (section 21 rule 4).
- `content.getDetails`: the optional member `timeGrid.minHandleSpacingSec`, the least distance that moves of the time grid keep between handles, which is implementation-defined.
- `content.editTimeGrid`: the timeGridSeed job repeats the checks of the call when it runs and fails with their errors, so `x-otcp.jobErrors` lists `NOT_FOUND`, `NOT_READY` and `BUSY`.
- Registries: reason codes `dialog_commits_on_close`, `split_out_of_range`, `merge_not_possible`, `trim_out_of_range`, `reference_ineligible`, `duplicate_track`, `track_limit`, `target_track_occupied`, `last_track`, `track_hidden`, `no_project_path` and `audio_setting_unavailable` (all `INVALID_ARGUMENT`) and `device_open_failed` (`IO_ERROR`); warning codes `SCHEME_GENERATED_NOTES`, `SHARED_CONTENT` and `UNDO_HISTORY_POSSIBLY_STALE`. No error kind or capability is added.
- Vector format: preconditions for the visible track count, open dialogs, the first-run onboarding, user-global preferences (tuning, hybrid mode, experimental features, recent projects), the current project file and the audio device; fades of given clips; project files that open, and that reference a missing media file, as given files; undo entries recorded before a track after the clip's track was deleted; the runner name `runner.arrangementRevision`; the state of everything that `given` leaves out; dialogs of kind `preferences` and `unknown`; `clipOnEveryTrack`, which puts a clip on every track slot whatever the number of slots. Coverage rule 6 also covers the params members `action` and `target`.
- Vectors for every new method, including the OpenTune behaviours their results report: deleting a track and saving over another project without `confirm` (`INVALID_ARGUMENT(confirm_required)`), opening a project with unsaved changes (`UNSAVED_CHANGES(project_dirty)`) and with `discardUnsaved`, the track-colour dialog that commits on close with and without `confirm`, a dialog of kind `unknown` that is closed only with `confirm`, deleting clips without `confirm`, preventing and closing the first-run overlay, split, merge and delete with `UPSTREAM_UNDO_DEFECT` and an undo refused with `UNSUPPORTED(undo_unsafe_build)`, the `trackIdMap` and the removed reference bindings of a track deletion, the loop flag without effect, preferences with `GLOBAL_PREFERENCE` and their revert recipes (at a tuning of 432 Hz and back at 440 Hz), notes generated and reference analysis queued by a selection in the `openDyne` scheme, a trim that undoes its shortened fades (`FADES_RECLAMPED`), `NOT_SAVED_IN_PROJECT`, a project opened with a missing media file (`MEDIA_MISSING`), an audio device setup that is rolled back, and playback without an audio device (`NO_AUDIO_DEVICE`). Further vectors show `import.start` with `newTrack` when every track holds clips, the errors of the timeGridSeed job, and the undo rules of PROTOCOL.md section 15.3 rules 6 and 9.

### Clarified

- PROTOCOL.md section 15.3 rule 6, with the descriptions of `edit.undo`, `edit.redo` and `historyEntry`: a track deletion is a barrier in the undo and redo histories. An entry recorded through this API is possibly stale only when a deletion removed or moved down a track it addresses; such an entry fails without `force` with `UNDO_CONFLICT(stale_entry)`, and an entry whose tracks did not move is not possibly stale and is applied as usual, without a warning. An entry recorded in the UI is possibly stale after every deletion; without `force` it is applied with `UNDO_ENTRY_POSSIBLY_STALE`, and a call with `force`, which the end user asked for, applies it without that warning and clears `possiblyStale`. `origin` and `possiblyStale` therefore tell a client in advance which of the two happens. New vectors show these cases and the barrier set by `track.delete`.
- vectors/README.md: a runner decides whether a vector applies from the capabilities the instance reports before it establishes `given`; `withoutCapabilities` removes capabilities only while the vector runs.
- PROTOCOL.md sections 3.2 rule 3 and 3.3 rule 5: a JSON string, member names included, that escapes a lone surrogate is not valid JSON, so after authentication such a line gets `INVALID_ARGUMENT(parse_error)` with `id` null; the new vector `session/parse-error-lone-surrogate` shows it. This holds for every string of the line, also for the first value of a member name that appears twice, which a parser would drop.
- PROTOCOL.md section 5.5: on a normal stop the server may delete the ready file, but only while it still holds the `pid` and `instanceId` this instance wrote, so that it never deletes the ready file of a later start.
- PROTOCOL.md section 15.3 rule 6: an entry recorded through this API whose content a track deletion removed is applied as in the OpenTune UI: the step is used up and changes nothing (`noOp` with `UNDO_NO_EFFECT`).
- PROTOCOL.md section 15.3 rule 9 (new), with the descriptions of `edit.undo` and `edit.redo`: changes of a content without an undo entry (writes that are not undoable, notes generated as a side effect) are never taken back. Entries recorded through this API put back only the aspects of a content that their own change touched, and no longer those that a later change without an undo entry changed; such a change clears the redo history. A step left with nothing to put back is `noOp` with `UNDO_NO_EFFECT`.
- `import.start`: with `newTrack`, when every track holds clips, the call fails with `INVALID_ARGUMENT(track_capacity)` instead of importing onto the active track. Its revert recipe, which deletes the imported clips with `arrangement.edit`, carries `requiresConsent: true`, because deleting clips needs the end user's consent; the same holds for the revert recipe of `arrangement.copy`.
- `project.open`: its revert recipe carries no expected token; the dirty check (`UNSAVED_CHANGES(project_dirty)`) keeps it from overwriting later work.
- `content.getNotes`: `detectedMidi` is a fractional MIDI number, the pitch OpenTune shows for the note, to 0.01 semitone or finer.
- `content.getDetails`: `autoModes.uiButtonRuns` is `reference` only when the clip has a reference binding, the instance reports `reference.v1` and the experimental features are on.
- `content.editTimeGrid`: where seeded handles lie and the minimum spacing of moves are implementation-defined, as in OpenTune's time tool; clients read the handles instead of assuming values.
- Registries: the descriptions of `confirm_required` (also deleting clips), `dialog_commits_on_close` (consent member `confirm`), `track_capacity` (also `newTrack`) and `REPLACES_ALL_NOTES` (data `{removedCount, createdCount}`).

## [1.0.0-rc.1] - unreleased

First release candidate of protocol major 1, and the first version of the specification. It defines every method of layers L2 to L5; the methods of layers L6 and L8 and the UI-bridge methods are listed under "Planned". Changes made while this release candidate is drafted are folded into this entry; from the `spec-v1.0.0-rc.1` tag on, every change is recorded under the version that makes it.

### Added

- PROTOCOL.md: conventions; scope and non-goals; versioning and compatibility rules; transport and framing (literal `127.0.0.1`, OS-assigned port, one JSON message per line, a JSON-RPC 2.0 profile without batches or server-initiated messages, request ids decided by value and echoed as plain integer literals); limits; rules before authentication; `session.hello` with fixed failure responses and server-proof verification; discovery files and their lifecycle, with private file permissions on every system; enabling the control API; capabilities and registries; clocks and unit suffixes; handles, whose type prefixes (`c:`, `p:`, `u:`, `j:`) keep the kinds apart; revision tokens; the readiness gate; jobs and cancellation per job kind; concurrency, busy checks and UI priority; the write result envelope; undo descriptors, revert recipes (which never carry the user's consent) and undo rules; read conventions; errors; warnings; the export contract; paths, file identity, renames that never replace an existing target, and untrusted strings; editing schemes; the layer table and the index of all 43 methods.
- Number request ids are limited to integers from 0 to 2^53-1. An id only pairs a response with its request, so negative and fractional ids carry no meaning, and excluding them avoids differences between JSON parsers in how such numbers are read and written back.
- An entry created in the OpenTune UI gets an `undoId` when `edit.undo` or `edit.redo` applies it, so that the revert recipe of that step (`edit.redo` or `edit.undo`) can name it without `force`.
- `edit.undo` and `edit.redo` with `force` need no `expectedUndoId` and ignore it when it is given. A call with `force` that applies an entry clears its `possiblyStale`, so the revert recipe of such a step, which never carries `force`, is a complete request.
- Notes in `changes` and `created` of a write result are referenced at the revision after the write, notes in `removed` at the revision before it, so that every note reference names a note that exists at its revision.
- `export.start` with `ifExists` `error` fails at once with `ALREADY_EXISTS(target_exists)` when the target already exists, so that clients get the answer without a job.
- An export records the revisions of its contents when all of them are ready and it starts writing the file, so that a revision that changes while the export waits, for example because an analysis finishes, does not fail it with `REVISION_CONFLICT(changed_during_export)`.
- A revert recipe whose method needs a capability the instance does not report is not given: `revert` is null there and the result carries `IRREVERSIBLE`. Imports therefore name `arrangement.edit` in their recipes only on instances that report `arrangement.v1`.
- `import.start` takes an optional `idempotencyKey`: a repeated call with the key of a retained import job returns that job instead of importing the files again.
- A params value can need a capability besides its method's (`x-otcp.valueCapabilities`); AUTO in reference mode needs `reference.v1`.
- SECURITY.md: threat model with mitigations and residual risks.
- Registries: 19 error kinds, reason codes, 26 warning codes, 17 capabilities. Reason codes for the methods of layers L3 to L5: `grid_not_seeded` (a time grid without handles), `track_capacity`, `audio_too_long`, `unsupported_format`, `too_many_channels` and `idempotency_key_reused` (imports), `reference_not_bound` and `placement_content_mismatch` (AUTO in reference mode), and `duplicate_handle` (a time-grid handle named twice).
- Schemas: shared types (among them keys, pitch shift, note parameters, time-grid handles, transport state and undo history), discovery file and ready file (each with a closed form for servers and an open form for clients), registry files, method files, test vectors.
- Method files: `x-otcp.jobErrors` and `$defs.jobResult` give the error kinds and the result of the job a method starts.
- Method schemas: `session.hello`, `session.info`, `job.get`, `job.cancel`, `project.get`, `content.getNotes`, `content.getPitchCurve`, `content.segmentNotes`, `content.getDetails`, `transport.get`, `prefs.get`, `app.getLog`, `import.start`, `export.start`, `content.setKey`, `content.autoTune`, `content.editNotes`, `content.setPitchShift`, `edit.getHistory`, `edit.undo`, `edit.redo`, `content.shiftTiming` and `content.editTimeGrid`. The reference mode of `content.autoTune` is defined with its params, its capability and its job; its full behaviour follows with `content.analyzeReference`.
- Vector format: `extraCapabilities`; preconditions for clips with their analysis state, notes, key, pitch shift, time grid and reference binding, for files and paths (among them files that cannot be decoded, and the name an export with `ifExists` `rename` writes), for the undo and redo histories, the editing scheme, the unsaved-changes flag and the errors of given jobs; runner names for unknown and stale handles, for the last track slot and for a track slot that does not exist; coverage rules for every `op`, `mode`, `kind` and `layout` value, for every method-specific error kind and for the whole write envelope.
- Vectors for the session layer (rules before authentication and their connection limits, authentication, version negotiation, hello params and session limit, repeated hello, line length, blank lines, parse errors, batches, notifications, invalid requests, request id forms, duplicate ids, the in-flight limit, unknown methods, missing capabilities, unknown params), for jobs, and for every method of layers L2 to L5, including the OpenTune behaviours the results report: notes dropped at the edges of an AUTO range, AUTO that replaces all notes, a pitch shift that does not transpose the key, undo conflicts, undo steps without effect, undo entries the server refuses, uncorrected contents in exports, exports stopped by a change or by the export lock, and notes generated because an import selects the clip in the openDyne scheme.

### Planned

- Method schemas and vectors for `ui.getState`, `ui.dismiss` and the methods of layers L6 and L8 in a later release candidate of 1.0.0.
